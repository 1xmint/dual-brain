# Replit Cost Gate

Use this before turning Replit into an active lane.

## Core Truth

Replit can save time while still spending credits, compute, deployment usage,
or operator attention.

Treat it as a budgeted optional surface, not as free infinite cloud labor.

## Use Replit Only If One Of These Is True

- the local setup friction is the main blocker
- a cloud demo or publish surface is the actual goal
- auth or database setup is meaningfully easier there
- a bounded spike will likely save more time than it costs

If none of those are true, stay local.

## Ask Before Launch

1. What exact proof or artifact should come back?
2. Could local execution do this almost as easily?
3. Is publish/demo/auth/DB the real reason Replit helps?
4. What is the stop condition?
5. What has to be written back into local package truth?

If you cannot answer those cleanly, do not open the lane yet.

## Credit Protection Rule

Prefer:

- one bounded run
- one explicit output
- one clear return path into local truth

Avoid:

- repeated exploratory runs with no checkpoint discipline
- using Replit for low-value chores that your main local lane already handles
- paying cloud attention tax when the real problem is strategy, not execution

## Final Rule

If Replit is not reducing either setup burden, demo burden, or cloud-only
friction, it is probably the wrong lane for the job.
