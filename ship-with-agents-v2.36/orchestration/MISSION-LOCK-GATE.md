# Mission Lock Gate

Use this before a lane recommends the next slice, expands scope, or steps
up-stack into adjacent planning work.

## Core Truth

A lane title is not enough.

A meaningful lane should stay locked to:

- mission
- scope
- non-goals

until a real boundary-crossing decision is made.

## Resolve First

Read the smallest current truth that answers:

- what is this lane's mission
- what is explicitly in scope
- what is explicitly out of scope
- what workstream this lane serves
- what artifact currently defines the work

Preferred sources:

1. lane brain capsule
2. workstream story
3. active slice/checkpoint
4. active workstream row
5. launch packet or handoff

## Strong Behavior

- the lane names its mission before widening the conversation
- the lane rejects seductive adjacent work when that work belongs elsewhere
- the lane routes out-of-scope work to the correct owner instead of partially
  doing it here
- the lane turns "what's next?" into "what's next for this mission?"
- the lane does not treat a pasted correction for another lane as an implicit
  mission transfer

## Weak Behavior

- using one nearby dependency as an excuse to switch domains
- stepping from readiness into frontend planning because the ideas are related
- naming a new useful direction without first checking whether that direction
  belongs to this lane
- blindly obeying a buyer-pasted note even though it targets another lane or
  mission

## Final Rule

If the next move would still sound correct after replacing the lane name with a
different workstream, the lane is probably drifting.

If the lane also claims production, production-readiness, or integration, run
`references/PRODUCT-REALITY-GATE.md` before accepting rehearsal or sandbox work as the
main recommendation.
